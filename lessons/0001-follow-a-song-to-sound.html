nnplayer course · lesson 0001

跟着一首歌，走到发声

不逐个目录背诵。只追踪一次真实的“双击歌曲”，用一条链建立整个项目最重要的前后端心智模型。

约 10 分钟 目标：能复述播放主链 先修：基础 TypeScript / Rust 阅读

学完这一课，你应能回答两个问题：歌曲 ID 在哪里跨过前后端边界？真正下载音频字节并发声的又是谁？

先记住结论： Rust 不把音频字节流转发给前端。它只用登录 Cookie 换回一个真实播放 URL；随后由 WebView 中的 HTMLAudioElement 直接加载并播放这个 URL。

一张图看完主链

SongList 接收双击，传入歌曲列表与索引
→
Player Store 拥有队列、当前索引和播放模式
→

→

图中前半段在 src/，中间的原生边界在 src-tauri/，协议细节在 ncm-api-rs/。这三个目录正好对应三种不同责任。

逐步走一遍

  1. 界面只表达“用户想播哪一首”

    SongList.vue 的双击处理没有网络逻辑。它把当前列表和绝对索引交给 Player Store： 

    function playAt(idx: number) {
  void player.playList(props.songs, idx);
}
    src/components/SongList.vue · 175–176

  2. Store 只装配引擎并镜像状态

    player.ts 是 Playback Engine 的薄 Vue adapter：构造时注入 HTMLAudio runtime 和 Tauri URL 解析，把引擎状态镜像成 Pinia 响应式；动作全部直接转发，不再自己编排。 

    const engine = createPlaybackEngine({
  runtime: createHtmlAudioRuntime(),
  resolveSongUrl: (songId) => getSongUrl(songId).then((r) => r.url),
  ...
});

return { playList: engine.playList, next: engine.next, /* … */ };
    src/stores/player.ts · 39–44, 120–146

  3. Playback Engine 承担队列与音频副作用

    playbackEngine.ts 是无框架的深模块：拥有队列/播放模式，解析并缓存播放 URL、 同请求去重、切歌代际（Media Generation）隔离，并把 play / pause / waiting / ended / error 等媒体事件内化为状态转换； MediaSession 由装配层的 mediaSessionAdapter 接入。 

    const resolvedUrl = await resolveSongUrl(songId);
const handle = createActiveMedia(resolvedUrl);
await handle.play();
    src/playback/playbackEngine.ts · 150–160, 389–425

  4. 一个很薄的门面跨过 Tauri 边界

    前端不散落着裸 invoke。useNcmApi.ts 把命令名、参数类型和错误归一化集中在一起： 

    export function getSongUrl(songId: number) {
  return call<SongUrl>(Commands.GetSongUrl, { songId });
}

    Tauri 会把前端的 songId 映射到 Rust 参数 song_id。命令名 get_song_url 必须同时存在于前端常量和 Rust 的 generate_handler! 注册表中。

    src/composables/useNcmApi.ts · 99–120, 217–219

  5. Rust 命令负责可信边界

    get_song_url 先验证登录态，再从共享 AppState 取 Cookie 和 API 客户端， 请求 320 kbps（exhigh）地址，最后只挑出前端需要的 id / url / bitrate。 

    state.check_login().await?;
let cookie = state.cookie().await;
let resp = api.song_url_v1(/* id + exhigh + cookie */).await?;
Ok(SongUrl { id: song_id, url, bitrate: br })
    src-tauri/src/commands/music.rs · 88–122

  6. API crate 隐藏协议复杂度

    ncm-api-rs 的 song_url_v1 只描述端点与参数；公共 request 再统一处理 Cookie、设备指纹、请求头和加密。应用通常不应直接碰这些细节。 

    pub async fn song_url_v1(&self, query: &Query) -> Result<ApiResponse> {
    // 构造 ids、level、encodeType，再进入公共 request
}
    ncm-api-rs/src/api/song_url_v1.rs · 11 起

  7. 返回 URL，音频元素开始工作

    数据沿原路返回到 resolveSongUrl，被短时缓存；引擎经 Media Runtime 创建新的 媒体句柄（生产环境即一个新 Audio 元素），绑定事件，再调用 play()。从此，时间、缓冲、结束和错误都由媒体事件驱动状态。

重要排除项： ncm-api-rs 虽然也能以 Axum HTTP 服务独立运行，但 nnplayer 正常运行时把它作为 Cargo 路径依赖直接编译进 Tauri。 不需要另起一个本地 API 服务器。

谁拥有哪种状态？

状态 所有者 为什么放这里
队列、索引、播放模式 playback/playbackEngine.ts 播放行为的单一真源；stores/player.ts 镜像给 UI 共享
音频时间、缓冲、音量、媒体句柄 playback/playbackEngine.ts + htmlAudioRuntime.ts 与浏览器媒体 API 生命周期紧密相连，经 Media Runtime seam 隔离
Cookie、用户身份、API 客户端 src-tauri/src/state.rs 敏感且需要跨原生命令并发共享
协议参数、加密、设备信息 ncm-api-rs 与具体网易云接口协议绑定
